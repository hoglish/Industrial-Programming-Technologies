## Эксперимент с очередями выполнения

До запуска `npm run example:order` записать прогноз порядка меток. После запуска внести фактический порядок и объяснить каждую позицию.

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | AFDBEC | Первоначальный прогноз был неверным: предполагалось, что setTimeout(fn, 0) выполнится сразу после регистрации (F сразу после A), затем обработчик Promise (D), затем синхронное продолжение асинк-функции (B, E) и финальный синхронный log (C). Это отражало непонимание того, что весь код верхнего уровня выполняется синхронно до обработки любых очередей, а микрозадачи имеют приоритет над макрозадачами. |
| Фактический результат | ABCDEF | Синхронная часть (A, B, C) выполняется целиком в Call Stack. Затем Event Loop полностью очищает Microtask Queue — обработчик Promise.resolve().then(...) (D) и продолжение demonstrateAwait после await null (E). Только после этого берётся макрозадача из Task Queue — колбэк setTimeout (F). |

Отдельно указать:

- какие сообщения относятся к синхронному коду;
- какие продолжения попадают в очередь микрозадач;
- почему таймер с задержкой `0` не выполняется немедленно;
- изменится ли вывод, если удалить один из обработчиков Promise.

**1. Какие сообщения относятся к синхронному коду?**
К синхронной части выполнения относятся метки A, B и C:
- **A:** синхронный код — первый `log()` в начале скрипта, выполняется сразу при загрузке модуля.
- **B:** начало асинк-функции — `log()` внутри `demonstrateAwait()` до первого `await`. Асинхронная функция выполняется синхронно вплоть до первой точки приостановки (`await`).
- **C:** конец синхронного кода — последний `log()` в основном потоке скрипта.
Эти три сообщения выводятся подряд, без вмешательства Event Loop, потому что весь код верхнего уровня и код до первого `await` выполняется в одном проходе Call Stack.

**2. Какие продолжения попадают в очередь микрозадач?**
В Microtask Queue попадают две задачи:
- **D:** обработчик Promise — колбэк, переданный в `Promise.resolve().then(...)`. Метод `.then()` всегда планирует выполнение обработчика как микрозадачу, даже если промис уже разрешён (как в случае с `Promise.resolve()`).
- **E:** продолжение после `await` — код после `await null` внутри `demonstrateAwait`. Конструкция `await` внутри async-функции всегда планирует продолжение функции как микрозадачу, даже если ожидаемое значение уже готово (`null` разрешается мгновенно).
Порядок D перед E определяется порядком регистрации: `Promise.then` был вызван раньше, чем точка возобновления после `await`, поэтому D попадает в очередь первым.

**3. Почему таймер с задержкой 0 не выполняется немедленно?**
`setTimeout(fn, 0)` не означает «выполнить функцию сразу». Семантика этой записи:
1. Браузер/Node.js регистрирует таймер с минимальной задержкой (реально — не менее 4 мс по спецификации HTML для вложенных таймеров, но даже 0 мс достаточно для демонстрации принципа).
2. По истечении задержки колбэк помещается в Macrotask Queue (Task Queue).
3. Event Loop берёт задачу из Macrotask Queue только после двух условий:
   - Call Stack пуст (завершён весь синхронный код).
   - Microtask Queue полностью очищена.
Поэтому даже с `delay = 0` таймер выполняется последним — после всех синхронных инструкций и всех микрозадач (промисов и продолжений `await`). Задержка 0 лишь означает «поместить в очередь макрозадач как можно скорее», но не «обойти очередь».

**4. Изменится ли вывод, если удалить один из обработчиков Promise?**
Да, вывод изменится. Рассмотрим оба варианта:
- **Вариант А** — убрать `Promise.resolve().then(...)` (удалить D):
  В Microtask Queue останется только продолжение `await` (E).
  Вывод: `A → B → C → E → F`.
  Порядок остальных меток сохранится, просто исчезнет D.
- **Вариант Б** — убрать `await null` из `demonstrateAwait` (превратить в обычную функцию, удалить E):
  Без `await` функция `demonstrateAwait` становится полностью синхронной.
  `log("B")` и `log("E: продолжение...")` выполнятся подряд в одном синхронном проходе.
  Вывод: `A → B → E → C → D → F`.
  Метка E переместится между B и C, так как больше нет точки приостановки.
- **Вариант В** — убрать оба обработчика (и `Promise.then`, и `await`):
  Вывод станет полностью синхронным: `A → B → E → C → F`.
  F всё равно последняя, так как `setTimeout` всегда попадает в Macrotask Queue.

### Почему fetchFn передаётся в createApiClient
Передача `fetchFn` аргументом позволяет подменять реальную сеть на mock-функцию в модульных тестах (`npm run check:client`). Это делает тесты детерминированными, быстрыми и независимыми от состояния локального сервера. Также это явно показывает внешнюю зависимость модуля.

### Почему HTTP-ошибки проверяются отдельно от сетевых
`fetch` не отклоняет Promise при статусах 4xx/5xx — он успешно возвращает `Response`. Сетевая ошибка (DNS, отказ соединения, CORS) отклоняет Promise. Если поместить обработку `!response.ok` в общий `catch`, HTTP-ошибка будет ошибочно классифицирована как `network`. Поэтому перехват `fetch` и проверка `response.ok` разделены на два разных блока.

### Почему JSON после разбора всё равно проверяется по контракту
Синтаксически корректный JSON может иметь неверную структуру: `{ data: "не массив" }`, отсутствие обязательных полей, дубликаты id, несоответствие `meta.total` длине массива. Такой ответ не является пригодным для предметной логики. Проверка схемы (`isTask`, `isCategory`) защищает приложение от частичного использования повреждённых данных и преобразует нарушение в `invalid-response`.

### Правила проверки
- **Задача:** `id` — положительное безопасное целое; `title` — строка 1–100 символов после `trim`; `completed` — boolean; `priority` — low/medium/high; `categoryId` — положительное безопасное целое.
- **Категория:** `id` — положительное безопасное целое; `name` — строка 1–100 символов после `trim`.
- **Уникальность id:** коллекция не должна содержать повторяющихся `id`. Проверяется через `Set` за один проход.
- **meta.total:** должен точно совпадать с `data.length`. Несоответствие трактуется как нарушение контракта сервера.

## Последовательная и параллельная загрузка

Сравнить два сценария получения задач и категорий через `/debug/delay?ms=100`. Каждый сценарий выполнен три раза.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 218 | 215 | 221 | Время ≈ 2 × задержка. Второй запрос начинается только после завершения первого. |
| `Promise.all` | 112 | 109 | 114 | Время ≈ 1 × задержка. Оба запроса начинаются одновременно, ожидание завершается по медленнейшему. |

Измерения зависят от компьютера и не сравниваются с чужими значениями. Параллельная загрузка через `Promise.all` сокращает общее время ожидания примерно вдвое, потому что независимые ресурсы запрашиваются одновременно. `Promise.all` не создаёт параллельность сам по себе — он ожидает уже запущенные Promise. При отказе одного из них итоговый Promise отклоняется, но второй запрос автоматически не отменяется.

## Дополнительное задание

**Выбрано: Вариант А. Частичный результат через Promise.allSettled.**

Реализована отдельная функция `loadInitialDataSafe(filters)`, которая независимо получает задачи и категории. При отказе одного запроса результат другого сохраняется вместе со структурированным описанием ошибки.

**Контракт результата:**
```javascript
{
  tasks: { ok: true, value: [...] } | { ok: false, error: ApiError },
  categories: { ok: true, value: [...] } | { ok: false, error: ApiError }
}
```

**Три проверки:**
1. **Успех обоих запросов:** `tasks.ok === true`, `categories.ok === true`, оба содержат массивы.
2. **Ошибка задач при доступных категориях:** `tasks.ok === false`, `tasks.error.kind === "network"`, `categories.ok === true`, `categories.value.length === 3`.
3. **Ошибка обоих запросов:** `tasks.ok === false`, `categories.ok === false`, обе ошибки содержат `ApiError` с соответствующими `kind`.

Основной `loadInitialData` и его контракт не заменены. Расширение подключается отдельно через дополнительный импорт.

## Вывод

В ходе практической работы реализован модульный HTTP-клиент для учебного API с полной классификацией ошибок, ограничением времени и предметным слоем валидации схем. Все 18 проверок API, 26 модульных проверок клиента и 13 интеграционных проверок проходят без ошибок.

**Исправленные ошибки:**
1. Деструктуризация с дефолтами в сигнатуре `createApiClient` скрывала отсутствие обязательного `baseUrl` при передаче пустого объекта `{}`. Исправлено ручной проверкой ключей через `options.baseUrl`.
2. Отсутствие отдельной проверки `parsed.search` внутри блока парсинга URL позволяло некоторым некорректным базовым адресам проходить валидацию. Исправлено переносом проверки внутрь `try-catch`.
3. Использование оператора `??` для `fetchFn` не позволяло явно передать `null` как намеренную ошибку конфигурации. Исправлено через `Object.prototype.hasOwnProperty.call()`.

**Различие между типами ошибок:**
- **Ожидание Promise** — синхронная операция, возвращающая объект-обещание. Значение доступно только через `await` или `.then()`.
- **HTTP-ошибка** (`kind: "http"`) — сервер доступен и вернул ответ, но статус вне диапазона 2xx. Содержит `status`, `code`, `details`, `url`.
- **Сетевая ошибка** (`kind: "network"`) — ответ от сервера не получен (DNS, отказ соединения, CORS). Promise `fetch` отклоняется, `Response` не создан.
- **Неверный ответ сервера** (`kind: "invalid-response"`) — статус 2xx, но Content-Type не JSON, синтаксическая ошибка JSON или нарушение схемы данных.
- **Тайм-аут** (`kind: "timeout"`) — истекло заданное время ожидания. Отличается от отмены по `reason.name === "TimeoutError"`.
- **Явная отмена** (`kind: "aborted"`) — внешний `AbortController.abort()` вызван пользователем. Не маскируется под тайм-аут благодаря проверке причины отмены.
