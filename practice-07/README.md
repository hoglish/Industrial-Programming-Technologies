## Результат

Собрано React-приложение для управления задачами с хранением в памяти текущей страницы. Реализовано:

- отображение списка задач с названиями категорий;
- создание и редактирование задач с клиентской валидацией;
- переключение статуса и удаление после подтверждения через `confirm`;
- совместная фильтрация по поиску, статусу, приоритету и категории;
- статистика по полному набору (всего / выполнено / в работе);
- пустое состояние при отсутствии совпадений;
- безопасный вывод названия через `{task.title}` (без `dangerouslySetInnerHTML`).

**Ограничение хранения.** Данные живут только в состоянии React (`useState`). Перезагрузка страницы вызывает повторный рендер из `initialTasks` и `createInitialFilters()`, поэтому пользовательские изменения теряются. Это ожидаемое поведение ПР7 — сервер будет подключён в ПР8.

## Компоненты и состояние

**Владельцы состояния:**

| Состояние | Владелец | Почему здесь |
|---|---|---|
| `tasks` | `App` | Источник истины, нужен всем дочерним компонентам |
| `filters` | `App` | Определяют видимую выборку и должны пережить редактирование |
| `editingId` | `App` | Управляет режимом формы и сбрасывается из разных мест (удаление, отмена, успешное сохранение) |
| `draft`, `errors`, `message` | `TaskForm` | Локальны для формы, не нужны остальным компонентам |

**Производные данные** (вычисляются при каждом рендере, не хранятся):
- `visibleTasks = selectTasks(tasks, filters)` — список для отображения;
- `stats = getTaskStats(tasks)` — статистика по полному массиву;
- `editingTask = tasks.find(t => t.id === editingId)` — задача для формы.

Если хранить их в `useState`, пришлось бы синхронизировать при каждом изменении — это источник рассинхрона.

**Передача props и обратных вызовов.** Данные текут сверху вниз через props (`tasks`, `categories`, `stats`). Действия сообщаются наверх через функции-обработчики (`onToggle`, `onEdit`, `onDelete`, `onSave`). Карточка не меняет массив — она только сигнализирует родителю: «пользователь нажал "Завершить" у задачи с id=4».

**Сброс формы при смене задачи.** Форма рендерится с `key={editingId ?? 'new'}`. При переходе между задачами ключ меняется → React размонтирует старый экземпляр формы и монтирует новый → `useState` инициализируется заново. Это единственный корректный способ: `useState(initialTask)` применяется только при монтировании, не при обновлении props.

## Контрольные вопросы

**1. Чем JSX отличается от строки HTML?**
JSX — это синтаксический сахар над вызовами `React.createElement`. Он компилируется в JavaScript, а не парсится как HTML. Отсюда отличия: `className` вместо `class`, `htmlFor` вместо `for`, обязательное закрытие тегов (`<img />`), фигурные скобки `{expression}` для вставки значений. Вставка `{task.title}` автоматически экранируется — это защита от XSS, которой нет у `innerHTML`.

**2. Чем props отличаются от состояния?**
Props приходят от родителя и доступны только для чтения — компонент не должен их менять. Состояние (`useState`) принадлежит самому компоненту и меняется через сеттер, что вызывает перерендер. Props — «входные данные», состояние — «внутренняя память».

**3. Почему изменение обычной переменной не заменяет useState?**
Обычная переменная `let x = 0` живёт только в рамках одного вызова функции-компонента. При следующем рендере функция вызывается заново, и переменная инициализируется снова. `useState` сохраняет значение между вызовами, а его сеттер уведомляет React о необходимости перерендера.

**4. Когда требуется функциональная форма обновления состояния?**
Когда новое значение зависит от предыдущего (`setCount(c => c + 1)`) или когда в одном обработчике несколько обновлений подряд. React может батчить обновления, и прямое `setCount(count + 1)` дважды подряд даст `count + 1`, а не `count + 2`. Функциональная форма всегда получает самое свежее значение.

**5. Почему нельзя менять объект задачи внутри поверхностной копии массива?**
`[...tasks]` создаёт новый массив, но объекты внутри — те же ссылки. Изменив `next[0].completed = true`, мы изменим и исходный объект `tasks[0]`. React сравнивает ссылки и не увидит изменений, а значит не перерендерит зависимые компоненты. Нужно создать и новый массив, и новый объект: `tasks.map(t => t.id === id ? { ...t, completed: !t.completed } : t)`.

**6. Для чего списку стабильный key и почему индекс здесь не подходит?**
`key` позволяет React сопоставлять элементы между рендерами: понять, какие добавились, какие удалились, какие изменились. Индекс массива нестабилен при удалении из середины: задача с id=4 была на индексе 1, после удаления задачи с id=1 она окажется на индексе 0 — React решит, что это другая задача, и потеряет её локальное состояние (например, фокус или анимацию). `task.id` стабилен и уникален.

**7. Почему видимая выборка и статистика не хранятся в отдельных состояниях?**
Это производные данные от `tasks` и `filters`. Если хранить их в `useState`, придётся синхронизировать вручную при каждом изменении — это источник ошибок (счётчик отстаёт от списка, выборка не обновляется). Вычисляя их при рендере, мы гарантируем согласованность: данные всегда соответствуют текущему состоянию.

**8. Как дочерний компонент сообщает родителю о действии?**
Через функции, переданные в props. Родитель кладёт в prop `onToggle` свою функцию `handleToggle`, а карточка вызывает `onToggle(task.id)` в обработчике клика. Так компонент остаётся «глупым»: он не знает, что происходит с данными, только сигнализирует о намерении пользователя.

**9. Что делает поле управляемым?**
Связка `value={state}` + `onChange={handler}`. Значение поля всегда равно значению из состояния, а любое изменение пользователя проходит через handler и обновляет состояние. Поле становится «зеркалом» состояния. Без `value` поле неуправляемое (React его не контролирует), без `onChange` — только для чтения.

**10. Почему categoryId из select требует преобразования?**
HTML-атрибут `value` всегда строка, даже если передано число. В форме `categoryId` приходит как `'2'`, но в модели данных это число `2`. При валидации мы явно преобразуем регуляркой `/^[1-9]\d*$/` — это строже, чем `parseInt`, который принял бы `'2x'` как `2`.

**11. Как меняется состояние формы при изменении её ключа?**
React при смене `key` размонтирует старый экземпляр компонента и монтирует новый с нуля. Все `useState` в форме инициализируются заново. Это единственный надёжный способ сбросить форму при переходе от редактирования одной задачи к другой — `useState(initialTask)` применяет начальное значение только при первом монтировании.

**12. Почему подтверждение удаления не помещается внутрь функции обновления?**
Функции обновления состояния (`setTasks(prev => ...)`) должны быть чистыми: без побочных эффектов. `window.confirm` — побочный эффект (диалог), а в StrictMode React может вызывать функцию обновления дважды для обнаружения таких эффектов. Если `confirm` внутри, пользователь увидит два диалога. Правильно: сначала `confirm`, и только при подтверждении вызывать `setTasks`.

**13. Как отличить отсутствие задач от отсутствия совпадений фильтра?**
По длине исходного `tasks` и отфильтрованного `visibleTasks`. Если `tasks.length === 0` — это действительно пустой набор (после удаления всех). Если `tasks.length > 0` и `visibleTasks.length === 0` — есть задачи, но ни одна не подошла под фильтры. В обоих случаях выводится сообщение «По выбранным условиям задач нет.», но статистика (всего/выполнено/в работе) показывает реальный размер полного набора.

**14. Что проверяет npm test и чего он не проверяет?**
`npm test` проверяет только чистые предметные функции (`task-service.js`): валидацию, фильтрацию, статистику, операции изменения, отсутствие мутаций. Он **не** запускает React и не проверяет компоненты, рендеринг, обработчики событий, работу формы в браузере. Для компонентов нужны отдельные тесты с `@testing-library/react` или ручные сценарии из раздела 9.3.

**15. Какие части приложения потребуется изменить для подключения API в ПР8?**
- `App.jsx`: заменить локальные `tasks` на асинхронную загрузку через `useEffect`; добавить состояния `loading`/`error`.
- `handleSave`, `handleToggle`, `handleDelete`: сделать асинхронными, возвращать `Promise<boolean>`; повторный GET после мутации (как в ПР6).
- `TaskForm`: `onSave` станет асинхронным, форма должна блокироваться на время запроса.
- Добавить HTTP-клиент (`api-client.js`, `task-api.js` из ПР6) и обработку ошибок через `ApiError`.
- Добавить защиту от гонок запросов через `AbortController`.
- Убрать зависимость от `initialTasks` — данные придут с сервера.

## Вывод

В ПР7 освоен переход от DOM-манипуляций (ПР3–ПР6) к декларативному описанию интерфейса через React-компоненты. Ключевые усвоенные идеи:

- **разделение состояния и представления**: чистые функции предметной области (`task-service.js`) не знают про React, а компоненты не знают про HTTP;
- **неизменяемые обновления**: все операции возвращают новые массивы/объекты, иначе React не увидит изменений;
- **производные данные вместо синхронизации**: выборка и статистика вычисляются при рендере, а не хранятся отдельно;
- **однонаправленный поток данных**: props вниз, колбэки вверх, без прямых обращений между компонентами;
- **сброс формы через `key`**: надёжнее, чем ручная очистка полей.
