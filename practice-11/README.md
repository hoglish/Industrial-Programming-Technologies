## Модель данных

Созданы две сущности со связью «один ко многим» (одна категория — много задач):
1. **`categories`**: 
   - `id` (integer GENERATED BY DEFAULT AS IDENTITY, PRIMARY KEY)
   - `name` (text, NOT NULL, UNIQUE, CHECK: char_length 1–100, без пробелов по краям)
2. **`tasks`**: 
   - `id` (integer GENERATED BY DEFAULT AS IDENTITY, PRIMARY KEY)
   - `title` (text, NOT NULL, CHECK: char_length 1–100, без пробелов по краям)
   - `completed` (boolean, NOT NULL DEFAULT false)
   - `priority` (text, NOT NULL, CHECK IN ('low', 'medium', 'high'))
   - `category_id` (integer, NOT NULL, FOREIGN KEY REFERENCES categories(id) ON DELETE RESTRICT)
   - Создан индекс `tasks_category_id_idx` на поле `category_id`.

**Обоснование:**
- **Типы:** `text` для строк, `integer` для id, `boolean` для флага.
- **ON DELETE RESTRICT:** запрещает удалять категорию с задачами, предотвращая потерю данных.
- **CHECK vs NOT NULL:** `CHECK` не запрещает `NULL`, поэтому нужны обе проверки.
- **categoryId / category_id:** в SQL — `snake_case`, в API ПР10 — `categoryId`. В Q7 применён алиас `category_id AS "categoryId"`.
- **CHECK vs JS:** `char_length` и `btrim` в PostgreSQL считают реальные символы и обрезают только пробелы. JS `.length` использует UTF-16, а `.trim()` удаляет больше пробельных символов.

## Контрольные вопросы

1. **Почему название категории хранится отдельно от задач?**
Это принцип нормализации (устранение дублирования). При переименовании категории обновляется одна строка, а не сотни задач.

2. **Какие строки допускает связь «один ко многим» со стороны каждой таблицы?**
Со стороны категории — одна строка. Со стороны задач — множество строк, ссылающихся на один `id`.

3. **Почему CHECK не заменяет NOT NULL?**
`CHECK` пропускает `NULL`, так как результат проверки `NULL` не является `FALSE`. Для запрета отсутствия значения нужен `NOT NULL`.

4. **Что защищает внешний ключ при INSERT, UPDATE и DELETE?**
При `INSERT` и `UPDATE` не даёт вставить `category_id`, которого нет в `categories`. При `DELETE` (с `ON DELETE RESTRICT`) запрещает удалять категорию с задачами.

5. **Почему выбрано RESTRICT, а не CASCADE?**
`RESTRICT` защищает от случайной потери данных. При `CASCADE` удаление категории молча удалило бы все связанные задачи.

6. **Чем identity BY DEFAULT отличается от ручного назначения всех id?**
`IDENTITY` генерирует id автоматически. Режим `BY DEFAULT` позволяет и ручную вставку старых id (как в seed).

7. **Зачем после seed вызывается setval?**
Явные вставки не продвигают последовательность. Без `setval` следующая автоматическая вставка конфликтовала бы с существующим id.

8. **Почему после отката могут появиться пропуски в id?**
Последовательности работают вне транзакций, `nextval` не откатывается. Это штатное поведение, а не потеря строк.

9. **Чем LEFT JOIN отличается от INNER JOIN?**
`LEFT JOIN` возвращает все строки из левой таблицы, даже если справа нет совпадений. `INNER JOIN` — только совпадающие.

10. **Почему для пустых категорий нужен count(t.id), а не count(*)?**
`count(*)` считает строки соединения (для пустой категории вернёт 1), а `count(t.id)` игнорирует `NULL`.

11. **Чем WHERE отличается от HAVING?**
`WHERE` фильтрует строки до группировки, `HAVING` — уже сгруппированные строки после `GROUP BY`.

12. **Для чего нужен ORDER BY?**
Для детерминированного порядка вывода, так как без него порядок строк не гарантирован.

13. **Чем char_length и btrim отличаются от проверок JavaScript ПР10?**
SQL считает символы (Unicode code points), а JS — единицы UTF-16. `btrim` убирает только обычные пробелы, а JS `.trim()` — все пробельные символы.

14. **Почему изменение файла схемы не обновляет существующую базу автоматически?**
SQL-файл — это текстовый скрипт. База хранит уже применённую структуру в системном каталоге. Нужны `ALTER TABLE` или пересоздание базы.

15. **Почему данные PostgreSQL ещё не отображаются в клиенте ПР10?**
Сервер ПР10 всё ещё использует память (массивы в `store.js`). Подключение к базе (драйвер `pg`, параметризованные запросы) — задача ПР12.
