## Цель и результат

Цель работы — связать клиентские действия с серверными изменениями данных, сохранив согласованный HTTP-контракт и корректную обработку ошибок. В ходе работы были реализованы серверные операции записи: создание задач (`POST`), частичное обновление (`PATCH`) и удаление (`DELETE`). Сервер независимо проверяет типы и значения полей, назначает уникальные `id` и корректно обрабатывает ошибки, не изменяя данные при неверных запросах. React-клиент ПР8 успешно интегрирован с новым API и выполняет весь CRUD-цикл.

## Реализация

Самостоятельно были реализованы три файла:
1. `task-validation.js`: функция `validateTaskInput` проверяет наличие и типы полей. Собирает все ошибки в один объект `details` (с использованием `Object.create(null)`). Использует `Object.hasOwn` для корректной обработки `completed: false`. В `PATCH` не добавляет отсутствующие поля.
2. `store.js`: методы `createTask` (берет текущий `nextId`, добавляет `completed: false`), `updateTask` (частично обновляет только переданные поля, сохраняет исходный `id`), `deleteTask` (удаляет задачу, `nextId` не уменьшается). Возвращаются копии объектов.
3. `write-routes.js`: обработчики `POST` (возвращает 201 и заголовок `Location`), `PATCH` (возвращает 200, а при гонке с удалением — 404), `DELETE` (возвращает 204 без тела).

Инфраструктура `json-body.js` (лимит 16КБ, `strict: false`) и единый `errors.js` используются для формирования JSON-ответов об ошибках (400, 413, 415).

## Контракт

- **POST** `/api/tasks` → `201 Created`, заголовок `Location: /api/tasks/35`, тело `{"data": {"id": 35, ...}}`.
- **PATCH** `/api/tasks/4` (тело `{"completed": true}`) → `200 OK`, `{"data": {...}}`. Непереданные поля сохраняются.
- **DELETE** `/api/tasks/4` → `204 No Content` (без тела).
- **Ошибки**:
  - 400 `VALIDATION_ERROR` с детализацией по полям (например, если `categoryId` не существует).
  - 400 `INVALID_JSON` (если JSON сломан или тело пустое).
  - 400 `INVALID_ID`, 404 `TASK_NOT_FOUND`.

## Исправленный дефект

**Симптом:** при попытке создания задачи с несуществующей категорией задача всё равно создавалась.
**Причина:** валидатор проверял только тип `categoryId`, но не сверял его с реальным списком категорий в store.
**Исправление:** в `write-routes.js` перед вызовом валидатора извлекается `Set` существующих id (`store.listCategories()`), который передается в `validateTaskInput`. 
**Повторная проверка:** запрос с `categoryId: 999` теперь возвращает 400 и данные не изменяются.

## Контрольные вопросы

1. **Почему проверка формы не заменяет серверную валидацию?**
Проверку формы легко обойти (отключить JS, отправить запрос напрямую через Postman/curl). Сервер обязан самостоятельно проверять данные, чтобы защитить БД от мусора и атак.

2. **Чем частичное обновление отличается от замены записи?**
При `PATCH` отсутствующие в теле запроса поля сохраняют свои старые значения. При `PUT` (полная замена) отсутствующие поля стёрлись бы или сбросились к дефолтным.

3. **Как отличить отсутствующий `completed` от переданного `false`?**
Использовать `Object.hasOwn(value, 'completed')`. Проверка `if (value.completed)` ошибочно примет `false` за отсутствие поля.

4. **Почему строковый `categoryId` в query допустим, а в JSON-теле — нет?**
В URL все параметры передаются строками, их разбор — обязанность сервера. В JSON есть нативные типы, поэтому клиент обязан передавать число, а не строку `"2"`.

5. **Когда следует увеличивать `nextId` и почему нельзя брать длину массива?**
Сразу после добавления записи. Длина массива уменьшается при удалении, что привело бы к коллизии `id` (выдаче уже существующего). Счётчик только растёт.

6. **Что произойдёт с данными после перезагрузки браузера и после перезапуска API?**
Перезагрузка браузера ничего не меняет (данные на сервере). Перезапуск API сбрасывает массив к исходным 12 задачам, так как данные в памяти.

7. **Зачем POST возвращает 201 и Location?**
`201 Created` подтверждает создание ресурса. `Location` даёт URL, по которому созданный ресурс доступен.

8. **Почему DELETE 204 не должен содержать JSON?**
`204 No Content` по стандарту HTTP означает, что тела ответа нет. Клиент (и браузер) могут сломаться, пытаясь распарсить пустоту как JSON.

9. **Чем `INVALID_JSON` отличается от `VALIDATION_ERROR`?**
`INVALID_JSON` (400) — синтаксическая ошибка парсинга (битый JSON, пустое тело). `VALIDATION_ERROR` (400) — синтаксис верный, но данные не прошли бизнес-правила (например, пустой title).

10. **Как исключить частичное изменение при ошибке одного поля?**
Сначала валидатор собирает все ошибки и бросает исключение. Если ошибок нет — возвращается новый чистый объект. Только после этого вызывается `store.updateTask`. База обновляется атомарно.

11. **Почему нельзя бесконтрольно применять spread к `req.body`?**
Спред скопирует любые поля, включая `id`, `__proto__` или неизвестные ключи, что позволит клиенту подменить структуру записи.

12. **Почему CORS не является авторизацией?**
CORS ограничивает чтение ответов браузером с других доменов, но не мешает отправлять запросы скриптам, curl или Postman.

13. **Зачем повторно проверять результат `updateTask` после разбора тела?**
Пока парсилось тело, задачу могли удалить другим запросом. Если `updateTask` вернул `null`, нужно отдать 404, а не 200 с `data: null`.

14. **Почему успешный POST и неуспешный GET нельзя считать одной неудачной операцией?**
POST уже изменил сервер. Ошибка GET означает лишь проблему с обновлением экрана. Повторный POST приведёт к дубликату.

15. **Что именно проверяют тесты интеграции и что необходимо проверить в браузере?**
Тесты проверяют HTTP-контракт и адаптеры ПР8 без React. В браузере нужно проверять UI: блокировку кнопок, черновики, отображение ошибок и работу в реальном времени.
