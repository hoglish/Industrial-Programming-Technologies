## 1. Цель работы

Цель — связать интерфейс браузерного приложения с учебным HTTP API и организовать предсказуемое состояние интерфейса во время асинхронных операций.

В ходе работы отрабатывались: отправка GET, POST, PATCH и DELETE через `fetch`; передача JSON-тела и обработка ответов 200, 201 и 204; разделение общего HTTP-клиента, предметного API, контроллера и DOM-представления; вывод состояний `loading`, `ready`, `empty`, `error`; клиентская проверка формы до отправки запроса; повторная загрузка данных после изменения на сервере; отмена предыдущего запроса и защита от устаревшего ответа; безопасный вывод серверных данных как текста; модульная, интеграционная и браузерная проверка основных сценариев.

Полученный результат: в папке `practice-06` работает приложение, в котором категории и задачи поступают из учебного API, фильтры превращаются в query-параметры серверного запроса, задача создаётся, редактируется, переводится в другой статус и удаляется, сервер остаётся единственным источником данных, ошибки загрузки и изменения не разрушают уже показанный интерфейс, после обновления страницы сохраняются изменения, пока запущен API.

## 3. Реализация

### 3.1. HTTP-клиент

Клиент реализован в `src/api-client.js` функцией `createApiClient({ baseUrl, fetchFn, timeoutMs })`, которая возвращает объект с методом `requestJson(path, options)`.

Поддерживаются методы `GET`, `POST`, `PATCH`, `DELETE`. Метод нормализуется в верхний регистр; неизвестный метод отклоняется с `TypeError` до сетевого запроса; `GET` с телом отклоняется. К каждому запросу добавляется `Accept: application/json`. При наличии тела добавляется `Content-Type: application/json`, тело сериализуется через `JSON.stringify`. К запросам без тела `Content-Type` не добавляется, чтобы не вызывать лишний CORS preflight.

Порядок обработки ответа: сначала проверяется `!response.ok` — HTTP-ошибка преобразуется в `ApiError` с полями `status`, `code`, `details`, `url`; тело ошибки разбирается как JSON только при соответствующем `Content-Type`. Затем для `204` и `205` возвращается `null` до любой попытки разбора тела. Для остальных успешных ответов проверяется `Content-Type` и корректность JSON; неверный `Content-Type` и синтаксическая ошибка дают `ApiError` с `kind: "invalid-response"`.

Тайм-аут реализован через внутренний `AbortController`, связанный с внешним `AbortSignal`. По истечении времени вызывается `controller.abort(DOMException("Timeout", "TimeoutError"))`. Виды ошибок различимы по полю `kind`: `http`, `network`, `invalid-response`, `timeout`, `aborted`. Внешняя отмена не маскируется под тайм-аут.

### 3.2. Доменный API

Модуль `src/task-api.js` знает маршруты и схему данных, но не работает с DOM и не формирует пользовательские сообщения. Реализованы: `getTasks(filters, options)`, `getTaskById(id, options)`, `getCategories(options)`, `loadInitialData(filters, options)`, `createTask(draft, options)`, `updateTask(id, changes, options)`, `setTaskCompleted(id, completed, options)`, `deleteTask(id, options)`, `resetDemoData(options)`.

Фильтры нормализуются и валидируются до запроса. Схема ответа проверяется функциями `isTask` и `isCategory`; дополнительно проверяется уникальность `id` в коллекции и соответствие `meta.total` длине массива. Нарушение схемы преобразуется в `ApiError` с `kind: "invalid-response"`. Для `deleteTask` ожидается строго `null` (ответ 204); если сервер неожиданно вернул тело, создаётся `ApiError`. `loadInitialData` загружает задачи и категории параллельно через `Promise.all`.

### 3.3. Состояния интерфейса

Контроллер хранит последний список задач, категории, текущие фильтры, `editingId` или `null`, активный `AbortController` загрузки и номер последней загрузки.

Переходы состояний: `loading` — перед каждым сетевым запросом, `aria-busy="true"`; `ready` — после успешного ответа с непустым списком; `empty` — после успешного ответа с пустым списком, не считается ошибкой; `error` — при любом отказе, кроме отмены, показывается сообщение и кнопка повтора.

При повторной загрузке предыдущий запрос отменяется, состояние снова становится `loading`, старые карточки не накапливаются благодаря `replaceChildren`. Отмена при смене фильтра не показывается пользователю как ошибка. Если начальная загрузка завершилась ошибкой и категории ещё не получены, кнопка повтора снова вызывает `loadInitialData`.

### 3.4. Изменение данных

Создание: `POST /tasks` с телом `{ title, priority, categoryId }`. Сервер назначает `id` и `completed: false`. После ответа 201 выполняется повторный `GET /tasks` с текущими фильтрами.

Редактирование: `beginEdit(id)` заполняет форму данными задачи и выставляет `editingId`. При `submit` вызывается `PATCH /tasks/:id` только с изменяемыми полями. После успеха `editingId` сбрасывается, форма возвращается в режим создания.

Смена статуса: `toggleTask(id)` находит задачу в текущем снимке, вычисляет `!task.completed` и отправляет `PATCH` с `{ completed }`.

Удаление: `deleteTask(id)` отправляет `DELETE`, после 204 повторно загружает список. Если удаляется редактируемая задача, режим редактирования сбрасывается.

Сброс: `resetData()` вызывает `POST /debug/reset` и повторно загружает текущий фильтр.

Во всех случаях сервер остаётся единственным источником данных: локальная копия не записывается в `localStorage` и не изменяется в обход ответа сервера. Изменяющие операции выполняются по общей схеме: `setMutationPending(true)` → запрос изменения → `notify(...)` → повторный `GET` с текущими фильтрами → `setMutationPending(false)` в `finally`. Кнопки блокируются на время мутации.

### 3.5. Защита от устаревшего ответа

Используются два механизма. Первый — предыдущий запрос отменяется через `AbortController`. Второй — каждому запуску присваивается последовательный номер `sequence`, и результат применяется только при совпадении номера с последним запуском и при неотменённом сигнале.

Вторая проверка нужна даже при отмене: тестовый клиент, кэш или другая реализация источника может завершить операцию, не отреагировав на сигнал немедленно. Отмена при смене фильтра является ожидаемым управлением потоком, поэтому сообщение об ошибке пользователю не выводится.

## 6. Ответы на контрольные вопросы

1. **Почему `fetch` не отклоняет Promise при ответе 404?**
   `fetch` отклоняет Promise только при сетевой ошибке или отмене. Ответ 404 или 500 — это успешно полученный HTTP-ответ, поэтому Promise разрешается объектом `Response`. Статус проверяется явно через `response.ok`.

2. **Почему ответ 204 нельзя разбирать вызовом `response.json()`?**
   204 No Content означает успешный ответ без тела. `response.json()` на пустом теле выбрасывает `SyntaxError`. Поэтому клиент возвращает `null` до любой попытки разбора.

3. **Чем состояние `empty` отличается от `error`?**
   `empty` — нормальный результат успешного запроса, вернувшего пустой массив. `error` — отказ запроса (сеть, HTTP-ошибка, неверный формат). `empty` не показывает кнопку повтора, `error` показывает.

4. **Зачем отменять предыдущий запрос при смене фильтров?**
   Если два запроса запущены подряд, первый может завершиться позднее второго. Без отмены старый результат перезапишет новый фильтр. `AbortController` отменяет предыдущий запрос, а проверка `sequence` дополнительно игнорирует устаревший результат, если источник не отреагировал на сигнал.

5. **Почему после мутации список повторно запрашивается у API?**
   Сервер — единственный источник истины. Локальная копия не должна изменяться в обход сервера. Повторный `GET` с текущими фильтрами показывает только подтверждённое сервером состояние и автоматически применяет фильтр к результату мутации (например, задача исчезает из выборки после смены статуса).

## 7. Вывод

В ходе работы реализован браузерный клиент, связанный с учебным HTTP API. Все 70 проверок Node.js и 14 браузерных сценариев проходят без ошибок.

Связь компонентов: `dom-app.js` читает форму и фильтры и передаёт их контроллеру; контроллер вызывает методы `task-api.js`; `task-api.js` формирует запрос через `api-client.js`; ответ проверяется по схеме и возвращается в контроллер; контроллер обновляет состояние и вызывает методы представления; `task-view.js` строит карточки безопасно через `textContent` и `replaceChildren`.

Найденные и исправленные ошибки:
1. В `createTaskElement` не выставлялся класс `is-completed` для выполненных задач — браузерная проверка смены статуса не видела изменения. Исправлено добавлением класса при `task.completed`.
2. В `app-controller.js` `editingId` сбрасывался после `mutate` даже при ошибке мутации — следующая отправка формы создавала новую задачу вместо повторной попытки редактирования. Исправлено: `mutate` возвращает статус, `editingId` сбрасывается только при успехе.
3. Порядок проверок в `api-client.js`: ранний возврат по `content-length === "0"` стоял до проверки `!response.ok`, что могло скрыть HTTP-ошибку с пустым телом. Исправлено переносом проверки `!response.ok` выше.
4. При пустом справочнике категорий `submit` молча проваливал валидацию без понятного сообщения. Добавлена явная проверка `categories.length === 0` с сообщением пользователю.

Осознанные ограничения: состояние API хранится в памяти; одновременно работает один общий учебный набор; нет аутентификации; после каждой мутации запрашивается весь отфильтрованный список; интерфейс реализован без фреймворка. Эти ограничения не являются ошибками ПР6 и будут изменяться на следующих этапах курса.
