## Полученный результат

Реализован React-клиент учебного API с загрузкой, изменением данных и корректной обработкой асинхронных состояний. Основное задание работы — хук `useTaskData` в `src/hooks/useTaskData.js`. Остальные модули (`api-client.js`, `task-api.js`, `form-validation.js`, компоненты, `App.jsx`) либо перенесены из ПР6–ПР7, либо предоставлены готовыми в заготовке.

**Что реализовано в хуке:**

- загрузка задач и категорий через `api.loadInitialData` при монтировании и смене фильтров;
- состояния `loading` / `ready` / `error` и отдельное поле `mutationError`;
- отмена устаревших GET-запросов через `AbortController` и защиту от их запоздавших ответов;
- блокировка повторных мутаций через `useRef` (не через `useState`);
- операции `saveTask`, `toggleTask`, `deleteTask`, `resetData` с повторным GET после успеха;
- корректная работа в `StrictMode` (двойной setup/cleanup);
- отмена загрузки и активной мутации при размонтировании.

**Ограничения хранения данных.** Данные живут в памяти процесса учебного API (`api/server.mjs` хранит массив задач в замыкании). Пока процесс запущен, изменения сохраняются между перезагрузками страницы и между разными вкладками. После остановки процесса или выполнения `POST /api/debug/reset` возвращается исходный набор из 12 задач. База данных на этом этапе отсутствует — собственный сервер будет в ПР9–ПР10.

### Состав зависимостей эффекта загрузки

```javascript
useEffect(() => { /* загрузка */ }, [
  api,              // стабильная ссылка из config.js
  filters.q,        // извлечены из объекта, чтобы не создавать новую ссылку
  filters.completed,
  filters.priority,
  filters.categoryId,
  revision,         // счётчик для refresh()
]);
```

`snapshot` и `tasks` **не включены** в зависимости: это результат эффекта, а не вход. Если бы они были в зависимостях, каждый успех запускал бы новую загрузку — бесконечный цикл.

### Cleanup и служебные ссылки

- `useRef(mountedRef)` — признак, что компонент ещё смонтирован. После unmount не вызываются `setState`.
- `useRef(mutationControllerRef)` — контроллер активной мутации. Используется для немедленной блокировки двух синхронных вызовов (один `useState` с `pending` не успевает обновиться между ними) и для отмены при unmount.
- Локальная переменная `active` и локальный `controller` — на каждый запуск эффекта свои. В cleanup `active = false; controller.abort()`.

### Отличия от ПР7

| ПР7 | ПР8 |
|---|---|
| `tasks` в `useState`, операции меняют локальный массив | `tasks` приходят с сервера, операции — HTTP-запросы |
| `onSave` возвращает `boolean` | `onSave` возвращает `Promise<boolean>` |

| Перезагрузка страницы сбрасывает задачи | Задачи сохраняются, пока жив процесс API |

## Загрузка и изменения

### Как подавляются старые ответы

Для каждого запуска эффекта создаются:
1. свой `AbortController` — передаётся в `api.loadInitialData`;
2. локальная переменная `active = true`.

При смене зависимостей React вызывает cleanup: `active = false; controller.abort()`. После `await` проверяется `if (active && mountedRef.current)` — и успех, и ошибка запоздавшего запроса игнорируются.

Одного `AbortController` недостаточно: тестовый или другой источник данных может проигнорировать сигнал и всё равно вернуть ответ. Поэтому флаг `active` — обязательная вторая линия защиты.

### Как блокируется повторная мутация

Форма может быть отправлена дважды (двойной клик, медленная сеть). `useState` с `pending` не помогает: оба вызова видят `pending === false` до первого перерендера.

Решение — `useRef` для контроллера мутации:

```javascript
const mutate = async (operation) => {
  if (mutationControllerRef.current) return false;  // уже идёт
  const controller = new AbortController();
  mutationControllerRef.current = controller;        // блокировка немедленная
  try {
    await operation(controller.signal);
    setRevision(r => r + 1);                        // триггер нового GET
    return true;
  } catch (err) {
    setMutationError(err);
    return false;
  } finally {
    if (mutationControllerRef.current === controller) {
      mutationControllerRef.current = null;          // освобождаем только свой
    }
  }
};
```

Освобождение только своего контроллера важно: если старый вызов всё-таки завершился после нового, его `finally` не должен затереть ссылку новой мутации.

### Различие ошибки POST и ошибки GET

После успешной мутации запускается новый GET. Если GET падает:
- `status` становится `error`, `error` содержит ошибку GET;
- `snapshot` остаётся прежним (последний успешный);
- `mutationError` остаётся `null` — мутация-то прошла.

Сообщения выводятся в разных `role`: «Сохранено на сервере. Список обновляется.» и «Не удалось обновить список: ...». Пользователь понимает: запись создана, но список устарел — нужно нажать «Обновить».

### Что происходит с черновиком при ошибке

- **Ошибка валидации формы** — POST не отправляется, черновик сохраняется, ошибки полей показываются рядом с полями через `aria-describedby`.
- **Ошибка сервера (400, 500, сеть)** — POST отправлен, черновик сохраняется, ошибка показана как `mutationError`. Форма не очищается, пользователь может исправить и повторить.
- **Успех** — форма очищается (для создания) или возвращается в режим создания (для редактирования, `editingTask = null`).

## Контрольные вопросы

**1. Зачем для загрузки данных нужен эффект, а не запрос в теле компонента?**
Тело компонента выполняется при каждом рендере — запрос отправлялся бы десятки раз в секунду. `useEffect` запускается только при изменении зависимостей и после коммита рендера. Кроме того, эффект умеет возвращать cleanup-функцию для отмены запроса при unmount или смене зависимостей — в теле компонента такой возможности нет.

**2. Когда React вызывает cleanup?**
В трёх случаях: перед повторным запуском того же эффекта (изменились зависимости), при размонтировании компонента, и в StrictMode дважды при монтировании (setup → cleanup → setup) для обнаружения побочных эффектов.

**3. Почему callback эффекта не объявляется async?**
`useEffect` ожидает, что callback вернёт либо `undefined`, либо функцию очистки. `async`-функция возвращает Promise, который React не может интерпретировать как cleanup. Асинхронная функция объявляется внутри и вызывается отдельно.

**4. Какие зависимости нужны загрузке и почему в них нет snapshot?**
Зависимости: `api` (стабильная ссылка), четыре поля `filters` (по отдельности, чтобы не реагировать на новый объект с теми же значениями) и `revision` (счётчик для `refresh()`). `snapshot` — это результат эффекта, а не вход; включение его в зависимости создало бы бесконечный цикл «загрузка → успех → новый snapshot → новая загрузка».

**5. Почему стабильная ссылка на api важна?**
Если `api` создавался бы внутри компонента при каждом рендере, его ссылка менялась бы, и эффект перезапускался бы постоянно. Поэтому `api` создаётся один раз в `config.js` вне компонента и импортируется.

**6. Зачем кроме AbortController проверять актуальность ответа?**
`AbortController` отменяет клиентский запрос, но сам по себе не гарантирует, что ответ не придёт: mock-API в тестах или медленный сервер могут проигнорировать сигнал и вернуть результат. Флаг `active` — вторая линия защиты, которая запрещает `setState` независимо от того, пришёл ответ или нет.

**7. Почему защита от устаревшего результата нужна и в catch?**
Если быстрый запрос завершился успехом, а медленный — ошибкой, запоздавшая ошибка не должна портить свежий результат. Без проверки в `catch` устаревшая сетевая ошибка перезаписала бы актуальный `ready`-snapshot на `error`.

**8. Что проверяет дополнительный цикл StrictMode?**
Он симулирует размонтирование и повторное монтирование, выявляя эффекты без корректного cleanup: неотменённые подписки, незакрытые соединения, дублирующиеся запросы. Если cleanup написан правильно, пользователь не видит разницы; в Network появляется один отменённый пробный GET.

**9. Почему одной переменной pending в state недостаточно для двух синхронных вызовов?**
`setState` асинхронен и батчится. Если пользователь дважды быстро нажимает «Сохранить», оба вызова видят `pending === false` (React ещё не перерендерил), и оба уходят на сервер. `useRef` обновляется синхронно и немедленно блокирует второй вызов.

**10. Что означает true, возвращённое saveTask, если повторный GET завершился ошибкой?**
`true` означает, что **сама мутация** прошла успешно — сервер подтвердил создание/изменение. Результат последующего GET — это отдельная история: его ошибка попадает в `error`, а не в `mutationError`. Форма очищается, потому что запись действительно создана; пользователю предлагается нажать «Обновить».

**11. Почему нельзя автоматически повторять POST после тайм-аута?**
Клиент не знает, дошёл ли запрос до сервера. При тайм-ауте возможны три сценария: сервер не получил запрос, сервер обработал, но ответ потерялся, сервер обработал и отправил ответ (клиент просто не дождался). Автоматический повтор в двух из трёх случаев создаст дубликат. Пользователь должен сначала обновить список и убедиться, что записи нет.

**12. Почему смена фильтров не должна отменять мутацию?**
Смена фильтра — это отмена чтения (GET), а мутация (POST/PATCH/DELETE) — это отдельная операция со своим контроллером. Если бы они делили контроллер, быстрая смена фильтра во время сохранения отменила бы POST, и пользователь потерял бы введённые данные без понятной причины.

**13. Что происходит с серверной операцией после отмены клиентского ожидания?**
Ничего — сервер продолжает обработку и сохраняет запись. `AbortController` отменяет только ожидание на клиенте. Именно поэтому после отмены нужно обновить список перед повтором мутации: возможно, сервер уже выполнил операцию.

**14. Чем meta.total отличается от общего числа записей на сервере?**
`meta.total` — это размер **отфильтрованной выборки**, которую вернул сервер. Если в базе 12 задач, но фильтр `completed=true` оставил 5, то `meta.total === 5`. Общий размер системы в этой работе не отдаётся сервером; надпись «Всего задач в системе» для этого значения была бы некорректной.

**15. Какие сценарии не проверяются jsdom и требуют браузера?**
Реальный CORS (prelight OPTIONS между разными портами), видимый фокус и `:focus-visible`, поведение `window.confirm`, работа DevTools Network, взаимодействие нескольких вкладок с одним процессом API, производительность рендера на большом списке, визуальное отображение throttling.

В ПР8 освоен переход от локального состояния React к клиент-серверной архитектуре. Ключевые усвоенные идеи:

- **`useEffect` с cleanup** — единственный корректный способ синхронизировать компонент с внешним источником данных; тело компонента для этого не подходит.
- **Две линии защиты от устаревших ответов**: `AbortController` (отменяет запрос) + флаг `active` (игнорирует запоздавший результат).
- **`useRef` для немедленной блокировки** — там, где `useState` не успевает из-за батчинга.
- **Разделение результатов**: успех мутации и ошибка последующего чтения хранятся в разных полях (`mutationError` и `error`), чтобы пользователь понимал, что запись создана, но список устарел.
- **Сервер — источник истины**: клиент не дописывает задачи локально, не назначает id, не фильтрует массив — всё это делает сервер через query-параметры и ответ.
