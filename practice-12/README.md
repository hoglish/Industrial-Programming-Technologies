## Архитектура

Цепочка данных: **React-клиент → HTTP API (Express) → store → Pool (pg) → PostgreSQL**.

Слои:
- `routes.js` — принимает HTTP-запрос, вызывает валидацию и методы хранилища, формирует ответ. SQL **отсутствует**.
- `task-validation.js` — предметная валидация. SQL **отсутствует**.
- `query-builders.js` — формирует `{ text, values }` из проверенных фильтров и изменений.
- `store.js` — выполняет запросы через пул, не знает об HTTP.
- `db.js` — создаёт единственный `Pool` с лимитом 5 соединений.

Пул переиспользует соединения между HTTP-запросами.

## Реализованные запросы

| Операция | SQL и параметры | Фактический результат |
|---|---|---|
| Список и фильтры | `SELECT ... WHERE completed = $1 AND priority = $2 ... ORDER BY id` | 12 задач, фильтры работают |
| Чтение по id | `SELECT ... WHERE id = $1` | Возвращает задачу или `null` |
| Создание | `INSERT ... VALUES ($1, $2, $3) RETURNING ...` | 201, `id 35`, `Location` |
| Частичное обновление | `UPDATE ... SET title = $1 WHERE id = $2 RETURNING ...` | 200, только переданные поля |
| Удаление | `DELETE FROM public.tasks WHERE id = $1` | 204, `rowCount === 1` |
| Reset-транзакция | `BEGIN; DELETE; INSERT; setval; COMMIT;` на одном клиенте | 3 категории, 12 задач |

**Параметры `$1...$n`:** пользовательские значения передаются только через параметры, а не конкатенацией. Это защищает от SQL-инъекций.

**Формирование фиксированных SQL-фрагментов:** динамические части запроса выбираются из заранее заданных фрагментов (allowlist), имена таблиц и колонок не подставляются извне.

**Экранирование `%`, `_`, `\`:** в `ILIKE` эти символы имеют специальный смысл. Функция `escapeLikePattern` экранирует их, а в SQL добавляется `ESCAPE '\'`.

**Отображение `category_id AS "categoryId"`:** двойные кавычки сохраняют регистр, иначе PostgreSQL вернёт `categoryid`, что нарушит контракт API.

## Контрольные вопросы

1. **Почему для веб-сервера используется Pool, а не новое соединение на каждый запрос?**
Создание физического соединения с PostgreSQL — дорогая операция. Пул переиспользует уже открытые соединения.

2. **Чем pool.query отличается от client.query внутри транзакции?**
`pool.query` берёт любое свободное соединение и возвращает его обратно. `client.query` выполняется строго на конкретном клиенте, что обязательно для транзакций.

3. **Почему все команды транзакции должны выполняться на одном клиенте?**
Состояние транзакции привязано к сессии соединения. Если `BEGIN` на одном клиенте, а `INSERT` на другом, второй запрос выполнится вне транзакции.

4. **Что произойдёт, если не вызвать client.release()?**
Клиент останется занятым навсегда. Пул исчерпается, новые запросы будут висеть в ожидании.

5. **Почему параметры защищают значения, но не имена колонок?**
Параметры `$1` — это только подстановка значений. Имена таблиц и колонок нельзя параметризовать.

6. **Зачем фиксировать порядок динамических условий и полей UPDATE?**
Для детерминированного SQL и корректного порядка параметров `$1..$n`.

7. **Почему %, _ и \ требуют отдельной обработки в ILIKE?**
В `LIKE/ILIKE` это шаблонные символы. Для буквального поиска их нужно экранировать, а в запросе указать `ESCAPE '\'`.

8. **Зачем писать AS "categoryId", а не AS categoryId?**
Без кавычек PostgreSQL приведёт алиас к нижнему регистру (`categoryid`), что нарушит контракт API ПР10.

9. **Почему POST не должен самостоятельно вычислять следующий id?**
`count(*) + 1` или `max(id) + 1` при параллельных запросах дают одинаковые значения и вызывают конфликт PK.

10. **Чем отсутствие строки в SELECT отличается от ошибки запроса?**
Отсутствие строки — успешный ответ с `rows = []`. Ошибка запроса — исключение. Для «не найдено» используется `rows[0] ?? null`.

11. **Зачем нужен RETURNING в INSERT и UPDATE?**
Возвращает вставленную или обновлённую строку одним запросом.

12. **Почему UPDATE после предварительного GET всё равно может вернуть ноль строк?**
Между `requireTask` (GET) и `UPDATE` другой клиент мог удалить запись.

13. **Почему проверка категории в JavaScript не заменяет FOREIGN KEY?**
Между проверкой в JS и INSERT другой запрос может удалить категорию. `FOREIGN KEY` атомарно гарантирует целостность.

14. **Почему приложение проверяет SQLSTATE, а не текст ошибки PostgreSQL?**
Текст ошибки локализован и может меняться. `SQLSTATE` — стандартный пятисимвольный код.

15. **Какие сведения об ошибке базы нельзя отправлять клиенту?**
Пароль, строку подключения, SQL, stack trace, имя constraint, detail.

16. **Чем постоянство после обновления страницы отличается от постоянства после перезапуска API?**
Обновление страницы сохраняет данные в памяти сервера ПР10. Перезапуск процесса в ПР10 сбрасывает их. В ПР12 данные в PostgreSQL сохраняются в обоих случаях.

17. **Почему reset нельзя оставлять публичным в рабочем приложении?**
Он удаляет все данные без авторизации. В рабочем приложении reset должен быть отключён.

18. **Что гарантирует ROLLBACK и чего он не гарантирует для sequence?**
`ROLLBACK` отменяет изменения строк. Но `nextval` (и `setval`) не откатываются: sequence уже продвинулась.

19. **Почему npm test без DATABASE_URL не подтверждает реальную интеграцию?**
DB-тест пропускается (`skipped`). Без реальной базы не проверяются SQL, транзакции и FK. Обязателен `npm run check:db`.

20. **Какие части решения потребуется изменить при добавлении пользователей и авторизации?**
Нужны таблицы `users`, поле `user_id` в `tasks`, middleware аутентификации, фильтрация задач по владельцу, проверка прав на PATCH/DELETE.

## Вывод

Сопоставление ПР10 и ПР12: в ПР10 данные хранились в памяти процесса и сбрасывались при перезапуске. В ПР12 данные хранятся в PostgreSQL и сохраняются после остановки и повторного запуска API. 
Ограничения решения: reset доступен без авторизации (только для учебных целей); отсутствуют миграции; нет разграничения прав пользователей.
